# Design: Document-RAG для Q&A по изученному источнику

**Дата:** 2026-05-29
**Статус:** approved (дизайн), реализация — этап 1 (модуль + E2E-скрипт)
**Ветка:** 019-ns-vstar-dpo

## Проблема

Пользователь хочет проверить: может ли MITS корректно отвечать на вопросы по
PDF-статье **после её изучения**. Разведка кодовой базы вскрыла структурный
разрыв:

- При ingest полный текст источника сохраняется в SQLite `SourceTable.content`,
  из него строится **дистиллированный** граф концептов (узлы = определения в
  1-3 предложения), но **исходный текст в путь ответа не попадает**.
- `TutoringRAG.retrieve_context()` (`src/knowledge/rag_retriever.py`) достаёт
  только подсказки/типовые ошибки из статичных JSON — никогда не обращается ни к
  `SourceTable`, ни к чанкам документа.
- `TutoringContext` **не имеет поля `chunks`**; при этом
  `orchestrator_service.py:1146` уже ссылается на `rag_context.chunks` (обёрнуто
  в try/except → молча падает в warning). Прямое свидетельство: document-RAG
  задумывался, но проводку не дописали.

**Вывод:** без document-retrieval звена тьютор физически не может ответить на
конкретный фактический вопрос по статье. Это надо достроить.

## Решение (этап 1: модуль + честный E2E)

Выбран поэтапный путь: сначала переиспользуемый модуль + E2E-скрипт с живой
моделью (низкий риск, живой чат не трогаем). При успехе — этап 2: интеграция в
`TutoringContext.chunks` + orchestrator (отдельная задача).

### Подход к извлечению

Эмбеддинги `paraphrase-multilingual-MiniLM-L12-v2` (та же модель, что у
`TutoringRAG`), косинус top-k. Ловит переформулированные вопросы. Fallback на
keyword-overlap, если sentence-transformers недоступен. Отвергнуто: чистый
keyword (проваливает парафразы), stuff-the-whole-doc (32-106 стр. не влезают
осмысленно в контекст, размывают внимание модели).

## Компоненты

### 1. `src/knowledge/document_retriever.py` (переиспользуемый модуль)

| Юнит | Назначение | Зависимости |
|------|-----------|-------------|
| `RetrievedChunk` (dataclass) | `text, source_id, chunk_index, score` | — |
| `DocumentRetriever.index(source_id, text) -> int` | чанкинг (`chunk_text`, ~1000 симв./150 overlap) → эмбеддинг → кэш; возвращает #чанков | `chunk_text` из source_analyzer, sentence-transformers |
| `DocumentRetriever.retrieve(query, source_ids=None, top_k=5, min_score=0.0) -> List[RetrievedChunk]` | косинус top-k по проиндексированным чанкам | numpy |
| `DocumentRetriever.to_prompt_context(chunks) -> str` | блок «МАТЕРИАЛ ИЗ ИСТОЧНИКА: …» для промпта | — |

**Контракт:** что делает — извлекает релевантные фрагменты изученного документа;
как использовать — `index()` один раз, `retrieve()` на каждый вопрос; от чего
зависит — sentence-transformers (с graceful fallback на keyword).

Это ровно то, что на этапе 2 ляжет в `TutoringContext.chunks` и в промпт
тьютора — модуль спроектирован под переиспользование, не под одноразовый тест.

### 2. `scripts/knowledge/document_qa_e2e.py` (E2E-демонстрация)

Поток:
0. Проверка/рестарт llama-swap (:8090, `mits-tutor`).
1. Извлечь текст PDF `docs/diploma/Фирсов_ВКР_бакалавр.pdf` (текстовый слой,
   `fitz.get_text()` — vision не нужен).
2. `DocumentRetriever.index()` — «изучение».
3. 6-8 вопросов с эталонными ответами по конкретным фактам документа (FID и др.).
4. **Контрольная абляция** на каждый вопрос через одну живую модель:
   - **A (closed-book):** без контекста — что модель знает «из головы».
   - **B (open-book):** с извлечёнными top-k чанками.
5. Оценка корректности (см. ниже) → таблица A vs B + вердикт.

## Поток данных

```
PDF ──fitz.get_text──> text ──index()──> [эмбеддинги чанков]
                                              │
вопрос ──┬─ A: промпт(вопрос) ───────────────┼──> mits-tutor ─> ответ_A ─┐
         └─ B: retrieve(вопрос)─> чанки       │                          ├─> судья ─> вердикт
            ──> промпт(вопрос+чанки) ─────────┴──> mits-tutor ─> ответ_B ─┘
```

## Методология (научная новизна для диплома)

Контроль closed-book vs open-book — это **абляция**: если B верен там, где A
путается, прирост точности обусловлен **извлечением из источника**, а не
априорным знанием модели. Поэтому взята *чужая* работа (Фирсов, FID/GAN) —
модель её гарантированно не видела, closed-book обязан проседать.

## Оценка корректности

LLM-судья: сравнивает ответ с эталонными фактами → вердикт
`correct/partial/wrong` + обоснование. Перекрёстная проверка на присутствие
ключевых фактов (sanity). **Логика вердикта = `TODO(human)`** — решение с
несколькими валидными вариантами (exact-match / keyword-overlap / LLM-judge),
отдаётся пользователю (Learn by Doing).

## Обработка ошибок

- llama-swap offline → понятное сообщение + команда запуска, exit 2 (как в
  `source_extraction_live_test.py`).
- sentence-transformers недоступен → fallback на keyword-overlap, лог-warning.
- Пустой текстовый слой PDF → ошибка с указанием, что нужен vision-путь (не наш
  случай: у Фирсова текстовый слой есть).
- Пустой `content` от модели (ловушка thinking-бюджета) → высокий `max_tokens`
  и/или `enable_thinking=false`.

## Тестирование

- Юнит-тесты `tests/test_document_retriever.py` (TDD): чанкинг, индексация,
  релевантность top-k (релевантный чанк ранжируется выше нерелевантного),
  fallback без эмбеддингов, пустой ввод.
- E2E-скрипт сам является интеграционным тестом на живой модели.

## Вне scope (этап 2, отдельная задача)

Интеграция в живой чат: поле `chunks` в `TutoringContext`, наполнение из
`SourceTable` по сессии, проводка в `orchestrator._build_user_prompt`, починка
мёртвой `rag_context.chunks` в `orchestrator_service.py:1146`.
