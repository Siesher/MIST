## WebSocket-протокол

Сократический диалог требует немедленной обратной связи: пользователь должен видеть ответ модели по мере его генерации, а не ожидать полной готовности текста. Для этого в системе реализован WebSocket-стриминг токенов — двунаправленный постоянный канал между браузером и бэкендом.

[Рис. N: sequence diagram стриминга — Browser → FastAPI → AgentOrchestrator → LLMClient → Ollama]

### Формат сообщений

Протокол определяет четыре типа сообщений клиент → сервер и пять типов сервер → клиент:

**Клиент → сервер**:

| Тип | Поля | Назначение |
|-----|------|------------|
| `chat` | `content`, `mode`, `session_id` | Отправка сообщения пользователя |
| `ping` | — | Поддержание соединения (heartbeat) |
| `abort` | `generation_id` | Принудительная остановка генерации |
| `mode_change` | `mode` | Переключение режима (chat/guided/task) |

**Сервер → клиент**:

| Тип | Поля | Назначение |
|-----|------|------------|
| `token` | `content`, `generation_id` | Очередной токен от LLM |
| `thinking` | `content`, `generation_id` | Токен из thinking-блока `<think>` |
| `done` | `generation_id`, `usage` | Завершение генерации |
| `error` | `code`, `message` | Ошибка обработки |
| `pong` | `timestamp` | Ответ на ping |

`generation_id` — UUID, уникальный для каждого ответа; используется фронтендом для корректного связывания потока токенов с соответствующим сообщением в Zustand-сторе.

### Жизненный цикл соединения

WebSocket-соединение устанавливается при открытии страницы чата и поддерживается на протяжении всей сессии. При разрыве соединения фронтенд автоматически переподключается с exponential backoff (500 мс → 1 с → 2 с → 4 с, максимум 5 попыток). Heartbeat (ping каждые 30 с) предотвращает закрытие соединения NAT/proxy по таймауту.

## Архитектура моста sync→async

Языковая модель в Ollama генерирует токены **синхронно**: функция `LLMClient.generate_stream()` возвращает обычный Python-генератор (`Generator[str, None, None]`). FastAPI, напротив, работает в асинхронной среде (asyncio event loop) и требует, чтобы WebSocket-обработчик являлся корутиной (`async def`).

Наивное решение — запустить синхронный генератор прямо в async-функции — заблокирует event loop на время генерации каждого токена, что сделает сервер невосприимчивым к другим запросам. Правильное решение: выполнять синхронный генератор в отдельном потоке через `ThreadPoolExecutor`, а результаты передавать в основной event loop через `asyncio.Queue`.

### Реализация моста

```
[sync thread: LLMClient.generate_stream()]
         │  token
         ▼
[asyncio.Queue]     ← put_nowait() из потока
         │  await queue.get()
         ▼
[async WebSocket handler]
         │  await ws.send_json({"type": "token", ...})
         ▼
[Браузер]
```

Схема работы:

1. Оркестратор запускает `asyncio.get_event_loop().run_in_executor(executor, sync_generator_runner, queue)` — синхронная генерация выполняется в пуле потоков.
2. `sync_generator_runner` итерирует `generate_stream()` и вызывает `loop.call_soon_threadsafe(queue.put_nowait, token)` для каждого токена.
3. WebSocket-корутина в event loop ожидает `await queue.get()` и немедленно отправляет токен клиенту через `await websocket.send_json(...)`.
4. Специальный sentinel-объект (например, `None`) сигнализирует об окончании потока.

Данный паттерн (ThreadPoolExecutor + asyncio.Queue) является стандартным для интеграции синхронных IO-bound операций в asyncio-приложения [см. документацию Python asyncio].

### Параметры пула потоков

`ThreadPoolExecutor` инициализируется с `max_workers=4` — это позволяет обслуживать до 4 параллельных WebSocket-сессий с потоковой генерацией одновременно. Ollama также настроен на `--parallel 3` (llama-server), что является реальным ограничителем параллелизма; четвёртый поток в executor используется для буферизации без блокировки.

## Парсинг thinking-блоков

Qwen3.5-9B в режиме `enable_thinking=True` начинает ответ с тегов `<think>...</think>`, содержащих внутренние рассуждения модели (chain-of-thought). Эти токены должны быть отделены от финального ответа и переданы клиенту с иным типом сообщения (`"thinking"` вместо `"token"`).

Парсер реализует простой конечный автомат с тремя состояниями:

```
NORMAL → (встречен '<think>') → IN_THINK
IN_THINK → (встречен '</think>') → POST_THINK
POST_THINK → NORMAL (если встречен следующий '<think>') → ...
```

В состоянии `IN_THINK` токены отправляются с типом `"thinking"`. Фронтенд отображает thinking-контент в отдельном сворачиваемом блоке с иконкой «💭», что позволяет пользователю видеть ход рассуждений модели.

`ThinkingBudgetProcessor` встроен в парсер: он отслеживает число токенов в thinking-блоке и при достижении 90% от бюджета (1500 токенов) принудительно повышает логит закрывающего тега `</think>` на +5,0. При 100% бюджета все прочие токены получают логит $-\infty$. Это обеспечивает гарантированное завершение thinking-блока и снижает долю обрезанных completions с 100% до **14,3%**.

## Обработка ошибок в стриминге

При возникновении исключения в синхронном генераторе (таймаут Ollama, сетевая ошибка):

1. `sync_generator_runner` помещает объект-исключение в Queue.
2. Asyncio-корутина извлекает исключение и отправляет клиенту сообщение `{"type": "error", "code": "generation_failed", "message": "..."}`.
3. Фронтенд отображает уведомление об ошибке и предлагает повторную отправку.

WebSocket-соединение при этом **не закрывается** — пользователь может продолжить диалог без переподключения.

## Fallback: HTTP-режим

При невозможности установить WebSocket-соединение (корпоративный прокси, блокировка) фронтенд автоматически переключается на HTTP-режим: запрос отправляется на `POST /api/v1/chat`, ответ возвращается целиком после завершения генерации. В этом случае стриминг и thinking-блоки недоступны, однако базовый функционал диалога сохраняется.
