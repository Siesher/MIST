## Агентский tool-loop и педагогическая граница

Параллельно с конвейером агентов в системе реализован **внешний tool-loop** — стандартный OpenAI-совместимый цикл «модель → запрос инструмента → исполнение → результат → следующий ход модели», который выполняется поверх дообученной модели и предоставляет ей доступ к структурированной базе знаний и интернет-поиску. В отличие от конвейера агентов (раздел 2.3), где Python-код принимает все педагогические решения, а LLM только формирует финальную реплику, в tool-loop сама модель решает, какой инструмент вызвать и с какими параметрами.

Формально каждый раунд цикла описывается переходом

$$M_t = \text{LLM}(M_{t-1}, \mathcal{T}),\ T_t = \text{exec}(M_t.\text{tool\_calls}),\ M_{t} \leftarrow M_t \cup T_t,$$

где $M_t$ — история сообщений, $\mathcal{T}$ — реестр инструментов в формате OpenAI Functions, $\text{exec}$ — диспетчер, исполняющий вызовы и возвращающий результаты как сообщения роли `tool`. Цикл завершается, когда модель в очередном ходе не запросила ни одного инструмента (поле `tool_calls` пусто) либо достигнут лимит раундов `max_rounds = 7`.

## Состав инструментов

В системе зарегистрировано **двенадцать инструментов**, организованных в три педагогически независимые группы:

**Группа A — структурированная база знаний (SKI, 5 инструментов)**: `lookup_concept(topic)` возвращает определение и список типичных ошибок по теме; `get_solution_method(topic)` — пошаговый алгоритм решения; `get_worked_example(topic, difficulty)` — разобранный пример; `get_formula(topic)` — ключевые формулы; `get_prerequisites(topic)` — список пререквизитов. Источник — статический корпус карточек знаний (`src/knowledge/ski.py`), составленный лично автором по 40 STEM-навыкам.

**Группа B — навигация по графу знаний (Knowledge Forge, 5 инструментов)**: `explore_concept(id, student_id)` — соседи узла в графе с overlay-мастерством ученика; `diagnose_gap(id, student_id)` — поиск ближайшего непокрытого пререквизита; `suggest_next(student_id, domain)` — следующий концепт для изучения; `find_learning_path(target, student_id)` — кратчайший путь к целевому концепту, взвешенный по mastery; `get_learning_frontier(student_id, k)` — k концептов на границе ZPD. Реализация — `src/tools/navigator_tools.py`, бэкэнд — `PersonalizedNavigator` (раздел 2.4).

**Группа C — интернет-поиск (web, 2 инструмента)**: `web_search(query, max_results)` — поиск через DuckDuckGo без API-ключа (Python-пакет `ddgs`); `fetch_url(url, max_chars)` — скачивание страницы и приведение к plain-text через регексп-стрип HTML. Реализация — `src/tools/web_tools.py`.

Каждый инструмент задан как JSON-схема в формате OpenAI Functions, включающая имя, описание (читаемое моделью!) и спецификацию параметров. Описание `web_search`, в частности, содержит явное правило настойчивости — «если первая выдача нерелевантна, переформулируй и повтори, минимум две формулировки прежде чем сказать "не нашёл"» — без которого модель сдаётся после одного неудачного запроса.

## Педагогическая граница: режимы chat и guided

Все двенадцать инструментов доступны не одинаково во всех режимах диалога — это **сознательное педагогическое ограничение**, а не техническая оптимизация. Web-поиск в сократическом тьюторе анти-педагогичен: задача ученика — *прийти к ответу через размышление*, а не получить готовое решение по запросу «найди в интернете». Поэтому в `orchestrator_service.process_message_stream` реализован гейт регистрации инструментов по режиму:

| Режим | SKI (5) | Knowledge Forge (5) | Web (2) | Итого |
|---|---|---|---|---|
| `chat` (свободный диалог) | ✓ | ✓ | ✓ | 12 |
| `guided_learning` (сократический) | ✓ | ✓ | ✗ | 10 |
| `task_generator` | ✗ | ✗ | ✗ | 0 |

SKI и Navigator остаются доступны в guided, потому что они — **педагогический инструментарий**, а не источник ответов: `lookup_concept` возвращает list of common_errors, по которому модель формулирует точечный вопрос про вероятную ошибку ученика; `get_prerequisites` отвечает на вопрос «что не понимает ученик?», а не «как решить задачу?». Системный промпт guided-режима явно фиксирует контракт: «после вызова инструмента НИКОГДА не выдавай прямой ответ; инструмент — твоя подготовка, в ответе ученику — наводящий вопрос на основе полученной информации».

## Стабилизация tool-loop для reasoning-моделей

Дообученная модель Qwen3.5-9B относится к классу reasoning-моделей со встроенным чат-шаблоном `<think>…</think>`. На таких моделях стандартный OpenAI tool-loop регулярно срывается в характерный failure mode: после получения результата первого инструмента модель в `reasoning_content` пишет «Let me try a different query» — однако в `content` возвращает пустую строку и не эмиттит структурный `tool_calls`. Цикл воспринимает это как «финальный ответ» (отсутствие `tool_calls`) и выходит, оставляя пользователю пустоту.

В реализации `OpenAICompatLLMClient.chat_with_tools` для этого случая введён детектор зависания: если в очередном ходе $\text{content} = \emptyset \land \text{tool\_calls} = \emptyset \land \text{tools\_used}_{<t} = \text{True}$, цикл не завершается, а **инжектит дополнительное сообщение роли `user`** с инструкцией «Продолжи: либо вызови инструмент с другой формулировкой, либо дай итоговый ответ» — и переходит к следующему раунду. Дополнительно температура сэмплирования снижена с 1,0 (стандарт) до 0,6 для tool-loop — высокая температура у reasoning-моделей провоцирует «болтливый thinking», который собственно и приводит к зависанию.

## Визуализация: схемы и графики в чате

Помимо текста и формул, модель может встраивать в ответ **исполняемые блоки визуализации**, которые frontend отрисовывает в реальном времени:

**Mermaid** — для блок-схем, графов рассуждения, последовательностей. Модель выдаёт код в фенсированном блоке ```` ```mermaid ``` ````; компонент `MermaidBlock` (`frontend/src/components/chat/MermaidBlock.tsx`) парсит и отрисовывает диаграмму через библиотеку `mermaid` с темой midnight.

**Plotly** — для интерактивных графиков функций, гистограмм, тепловых карт. Модель выдаёт JSON `{"data":[...],"layout":{...}}` в блоке ```` ```plotly ``` ````; компонент `PlotlyBlock` рендерит через `react-plotly.js`.

**KaTeX** — для формул `$inline$` и `$$display$$`.

Все три рендерера объединены в маршрутизатор `SmartContent`, который выполняет регексп-сегментацию текста ответа на фенсированные блоки и направляет каждый сегмент к специализированному рендереру; остальной текст идёт через стандартный Markdown.

Самостоятельно реализовано **graceful degradation для Mermaid**: при сбое парсинга (модель часто помещает в node-labels недопустимые символы — формулы со скобками, знак равенства, `<br>`) компонент выполняет повторную попытку с санитизированными labels — внутри `[…]`, `{…}`, `((…))` удаляются `(`, `)`, `=`, `<br>` и математические глифы `√`, `²`, `³`, `±`, `×`. Это позволяет «закрыть глаза» на типичную небрежность модели и всё равно получить рендер.

## Связь с конвейером агентов

Tool-loop и конвейер агентов из раздела 2.3 не конкурируют, а образуют **двухуровневую архитектуру**: внешний цикл (Profiler → Planner → Tutor → Verifier) принимает педагогические решения и формирует системный промпт, после чего внутренний tool-loop исполняет финальный ход тьютора с доступом к инструментам. Knowledge Forge-навигатор используется обоими: Planner — для статического построения учебной траектории, tool-loop — для реактивных запросов модели во время реплики.

В результате архитектурное разделение остаётся чётким: за **долгосрочную педагогическую стратегию** отвечает Python-конвейер, за **тактическое использование справочников и графа** — сама дообученная модель через tool-вызовы. Это позволяет модернизировать любой слой независимо: добавление нового инструмента не требует переписывания агентов, а изменение стратегии планирования не затрагивает реализацию tool-диспетчера.
