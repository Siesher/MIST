## Паттерн «конвейер агентов»

Мультиагентная архитектура системы построена по паттерну **конвейера агентов** (agent pipeline), впервые применённому в контексте образовательных систем в работе GenMentor [9]. В отличие от архитектуры с единым монолитным агентом-тьютором, конвейерная декомпозиция обеспечивает: (1) разделение ответственности — каждый агент решает ровно одну подзадачу; (2) изолируемость отказов — сбой одного агента не блокирует обработку хода; (3) независимую замену компонентов — новый алгоритм планирования подключается без изменения интерфейсов соседних агентов.

Формально каждый агент описывается кортежем $A = \langle S, \mathcal{A}, \mathcal{O}, \tau, \rho \rangle$, где $S$ — пространство состояний, $\mathcal{A}$ — пространство действий, $\mathcal{O}$ — пространство наблюдений, $\tau : \mathcal{O} \times S \to S$ — функция перехода, $\rho : S \to \mathcal{A}$ — политика агента.

[Рис. N: блок-схема конвейера агентов Profiler→MentalModel→Planner→Tutor→Verifier]

## Агент Profiler (классификация и профилирование)

**Роль**: анализ входящего сообщения ученика и формирование структурированного профиля ошибки.

**Входы**: сообщение ученика $m_t$, история последних $n$ ходов сессии, текущий mastery-профиль из Knowledge Tracing.

**Выходы**: `StudentProfile` — объект с полями `topic` (тема обращения), `error_type` (классификация ошибки из 8 категорий: sign_error, operation_confusion, variable_misuse, incorrect_formula, domain_confusion, unit_error, scope_error, notation_confusion), `difficulty_level` (уровень запроса), `domain` (предметная область).

**Реализация**: промпт с few-shot примерами передаётся в LLMClient.generate() в JSON-режиме; ответ парсится с валидацией через Pydantic. При ошибке парсинга возвращается дефолтный профиль с `error_type=unknown`, что гарантирует продолжение конвейера.

**Интерфейс**:
```
Profiler.process(message: str, history: List[Turn], mastery: Dict[str, float])
    → StudentProfile
```

## Агент MentalModelAgent (Theory of Mind)

**Роль**: построение модели психического состояния ученика (Theory of Mind, ToM) на основе истории диалога. Агент позиционирован между Profiler и Planner — его вывод используется для ToM-aware re-ranking пробелов в Knowledge Forge.

**Входы**: сообщение ученика, профиль из Profiler, последние 3 хода сессии, граф-контекст текущего концепта, целевая тема.

**Выходы**: `BeliefState` — объект с полями:
- `active_misconception` — идентификатор предполагаемого заблуждения;
- `active_misconception_node_id` — ссылка на узел графа знаний;
- `predicted_reactions` — словарь предсказаний реакции ученика на каждую из стратегий (scaffolding, direct_hint, socratic);
- `confidence` — уверенность модели $\in [0, 1]$;
- `candidate_misconceptions` — список альтернатив.

**Реализация**: двухэтапный LLM-вывод через Ollama (параметр `think=False`, поскольку thinking-токены «съедают» бюджет output при JSON-режиме). На первом проходе формируется классификация; при неуспешном парсинге — повторный запрос с суффиксом `Re-output JSON only`. При любой ошибке возвращается `BeliefState.empty(confidence=0)`, при котором downstream-компоненты игнорируют ToM и применяют baseline-логику (graceful degradation).

**Интеграция в оркестратор**: стадия `MENTAL_MODEL` активируется флагом `enable_tom_agent` в ресурсном профиле. В Lite-профиле (CPU 16 ГБ) агент отключён из-за latency p50 = 11,5 с; в Standard и Max — включён.

**Интерфейс**:
```
MentalModelAgent.infer(student_message: str, student_profile: StudentProfile,
                       history: List[Turn], graph_context: str, topic: str)
    → BeliefState
```

## Агент Planner (стратегическое планирование)

**Роль**: выбор педагогической стратегии и формирование плана урока для тьютора.

**Входы**: `StudentProfile` от Profiler, `BeliefState` от MentalModelAgent, граф-контекст из Knowledge Forge (текущий путь, frontier, рекомендованный следующий концепт).

**Выходы**: `LearningPlan` — структурированный план с полями: `strategy` (название стратегии), `objective` (цель текущего хода), `hints` (список наводящих подсказок из RAG), `next_concept` (следующий навык в траектории), `scaffolding_level` (уровень поддержки 0–3).

**Поддерживаемые стратегии**: Planner реализует дерево принятия решений с 8 стратегиями:

| Стратегия | Условие активации | Описание |
|-----------|-------------------|----------|
| scaffolding | mastery < 0,3 | Максимальная поддержка, декомпозиция на минимальные шаги |
| guided_discovery | 0,3 ≤ mastery < 0,6 | Наводящие вопросы, ученик приходит к выводу сам |
| error_correction | active_misconception != None | Целенаправленное исправление конкретного заблуждения |
| problematize | mastery ≥ 0,7 | Постановка контрпримера для углубления понимания |
| consolidate | mastery ≥ 0,8, streak ≥ 3 | Закрепление через вариации задач |
| encourage | confidence ≤ 0,4 | Снижение тревожности, аффективная поддержка |
| extend | mastery ≥ 0,9 | Расширение на смежные концепты |
| review | recency > 7 дней | Повторение забытого материала |

**Интерфейс**:
```
Planner.create_plan(profile: StudentProfile, context: PlannerContext,
                    graph_context: GraphContext, belief_state: BeliefState)
    → LearningPlan
```

## Агент Tutor (языковая модель)

**Роль**: генерация сократического ответа на основе плана, контекста и истории диалога.

**Входы**: системный промпт (роль и правила сократического метода), `LearningPlan` от Planner, RAG-контекст (подсказки, worked examples, misconception fixes), история сессии.

**Реализация**: тьютор является наиболее ресурсоёмким агентом конвейера. Сборка контекста тьютора:

$$\text{context} = [\text{system\_prompt}] \| [\text{plan}] \| [\text{RAG}] \| [\text{history}_{-n}] \| [\text{message}]$$

Результат передаётся в `LLMClient.generate_stream()`, который возвращает синхронный генератор токенов; мост sync→async (ThreadPoolExecutor + asyncio.Queue) транслирует токены через WebSocket (раздел 2.6). Thinking-блок `<think>...</think>` парсится в реальном времени и либо фильтруется, либо отображается отдельно в интерфейсе.

Модель Qwen3.5-9B поддерживает режим контролируемого мышления (thinking mode, [2]). `ThinkingBudgetProcessor` ограничивает длину thinking-секции 1500 токенами: при достижении 90% бюджета к логиту `</think>` добавляется +5,0, при 100% все прочие токены получают $-\infty$. Это сокращает долю обрезанных completions с 100% до 14,3%.

**Интерфейс**:
```
Tutor.generate_stream(context: TutorContext) → Generator[str, None, None]
```

## Агент Verifier (верификация качества ответа)

**Роль**: многомерная проверка сгенерированного ответа тьютора.

**Входы**: сгенерированный ответ тьютора, условие задачи, `LearningPlan` (ожидаемая стратегия).

**Выходы**: `VerificationResult` с полями `score` $\in [0, 1]$, `passed` (score ≥ 0,7), `issues` (список обнаруженных проблем).

**Проверки**: верификатор выполняет 10 независимых проверок:

1. Отсутствие прямого ответа (no-spoiler): ответ не должен раскрывать решение напрямую.
2. Наличие вопроса: ответ содержит хотя бы один наводящий вопрос (regex).
3. Корректность математики: если ответ содержит вычисления, SymPy проверяет их.
4. Длина ответа: 50–600 токенов (слишком короткий или длинный ответ штрафуется).
5. Соответствие стратегии: тон ответа соответствует выбранной стратегии Planner'а.
6. Использование LaTeX: математические выражения оформлены в LaTeX-нотации.
7. Отсутствие повторения: ответ не дублирует предыдущие ходы дословно.
8. Педагогическая прогрессия: ответ продвигает ученика к цели, а не возвращает назад.
9. Аффективный тон: отсутствие пренебрежительных формулировок.
10. Структурная связность: ответ логически связан с предыдущим высказыванием ученика.

При `score < 0,7` верификатор инициирует retry: тьютор повторно генерирует ответ с расширенными инструкциями. Число попыток ограничено двумя (после чего возвращается лучший из имеющихся вариантов).

**Интерфейс**:
```
Verifier.verify(response: str, task: str, plan: LearningPlan) → VerificationResult
```

## Дополнительные агенты

**AffectiveAgent** — детектор эмоционального состояния ученика на основе RuBERT-модели. Активируется в Standard и Max профилях. Классифицирует сообщение ученика по шкале frustration / neutral / engaged; результат передаётся Planner'у для активации стратегии `encourage` при высоком frustration. В Lite-профиле заменяется эвристикой (количество знаков препинания, короткие ответы).

**TaskGenerator** — агент режима task_generator. Принимает тему и уровень сложности; генерирует задачу с условием, правильным ответом и разбивкой на шаги. Новые задачи сохраняются в SQLite и индексируются в ChromaDB для последующего RAG-поиска.

## Поток данных в конвейере

Последовательность обработки одного хода диалога:

1. Сообщение ученика $m_t$ поступает через WebSocket в `AgentOrchestrator`.
2. **PROFILER** → `StudentProfile` (latency: ~500 мс, LLM JSON-call).
3. **MENTAL_MODEL** → `BeliefState` (latency: ~11,5 с p50 на Standard; пропускается на Lite).
4. Knowledge Forge: `Navigator.diagnose_gap()` с ToM re-ranking → `GapDiagnosis`, `LearningPath`.
5. PathSlime: `run()` → k альтернативных траекторий (latency: 1–4 мс).
6. RAG: векторный поиск ChromaDB → hints, worked examples, misconception fixes.
7. **PLANNER** → `LearningPlan` (deterministic, ~10 мс).
8. **TUTOR** → streaming token generation (first token ≤ 3 с).
9. **VERIFIER** → `VerificationResult`; при `score < 0,7` → retry.
10. Обновление Knowledge Tracing (BKT + DKT) на основе результата верификации.
11. Фоновый `SessionAnalyzer` аккумулирует изменения графа знаний.

Асинхронная природа шагов 10–11 гарантирует отсутствие блокировки пользовательского потока после отправки ответа.

## Инварианты конвейера

Корректность конвейера поддерживается следующими инвариантами:

- **Graceful degradation**: при отказе любого агента (исключение, таймаут) соответствующий объект заменяется дефолтным (empty profile, empty belief, default plan). Тьютор в этом случае работает в режиме прямого чата без педагогических ограничений.
- **Монотонность mastery**: $m(\sigma_{t+1}) \geq m(\sigma_t) - \varepsilon$ при $\varepsilon = 0{,}05$ — допустимое отклонение, обусловленное вероятностным характером BKT.
- **Монотонность доверия ToM**: `BeliefState.confidence` не убывает при повторяющихся подтверждающих наблюдениях.
- **Идемпотентность верификации**: повторный вызов Verifier на одном и том же ответе даёт детерминированный результат.
