## Концепция трёхуровневой архитектуры

Проектируемая система построена по трёхуровневой (three-tier) архитектуре, разделяющей слой представления, слой бизнес-логики и слой данных. Такое разделение обеспечивает независимость развёртывания компонентов, изолируемость отказов и возможность замены технологий на каждом уровне без модификации смежных.

[Рис. N: блок-схема общей архитектуры]

На верхнем уровне расположен **фронтенд** — клиентское приложение, отвечающее за пользовательский интерфейс и WebSocket-соединение со средним уровнем. Средний уровень — **бэкенд** — представлен REST API и WebSocket-обработчиком; он координирует аутентификацию, персистентность и оркестрацию агентов. Нижний уровень — **AI Core** — объединяет мультиагентный конвейер, систему Knowledge Tracing, RAG-подсистему и LLM inference через Ollama.

## Уровень фронтенда

### Технологический стек и обоснование

Фронтенд реализован на **Next.js 14** (App Router) с **TypeScript** и **Tailwind CSS**. Выбор Next.js обусловлен следующими факторами:

- *App Router и React Server Components* позволяют разграничить серверную и клиентскую логику; страницы, не требующие интерактивности, рендерятся на сервере, снижая объём JavaScript-бандла.
- *Встроенная поддержка SSR* обеспечивает правильную индексацию и быструю загрузку первой страницы (First Contentful Paint).
- *TypeScript* как язык с системой статической типизации снижает число ошибок интеграции фронтенд–бэкенд за счёт совместной типизации API-контрактов.

Управление состоянием чата реализовано через **Zustand** — легковесный менеджер состояния без шаблонного кода, характерного для Redux. Математические формулы рендерятся через **KaTeX** непосредственно в браузере без сетевых запросов.

Компонентная библиотека **shadcn/ui** предоставляет набор доступных (accessibility-first) примитивов на основе Radix UI, стилизованных Tailwind CSS. Это обеспечивает консистентный визуальный язык при минимальных усилиях разработки.

### Ключевые компоненты фронтенда

Приложение состоит из пяти страниц: авторизация (`/login`), регистрация (`/register`), список сессий (`/`), активный чат (`/chat/[sessionId]`) и аналитика (`/analytics`). Взаимодействие с бэкендом осуществляется через два канала: REST API (HTTP/JSON) для управляющих операций (создание сессии, аутентификация, получение истории) и WebSocket для потоковой передачи токенов в режиме реального времени.

Хуки `useChat` и `useWebSocket` инкапсулируют логику WebSocket-соединения; Zustand-стор `chatStore` хранит текущие сообщения, статус соединения и режим отображения thinking-блоков.

## Уровень бэкенда

### Технологический стек и обоснование

Бэкенд реализован на **FastAPI** — асинхронном Python-фреймворке, выбранном по следующим соображениям:

- *Нативная поддержка async/await* критична для WebSocket-стриминга: фреймворк не блокирует event loop во время ожидания токенов от LLM.
- *Автоматическая генерация OpenAPI-документации* из аннотаций типов Pydantic снижает затраты на документирование API.
- *Встроенная поддержка WebSocket* через Starlette-слой позволяет обслуживать REST и WS из единого процесса.

**SQLAlchemy 2.0** предоставляет ORM с поддержкой asyncio; **SQLite** выбран в качестве СУБД по критерию портируемости (zero-config, единый файл, совместимость с любой ОС). При необходимости горизонтального масштабирования SQLite может быть заменён PostgreSQL без изменений кода ORM.

Аутентификация реализована через **JWT** (библиотека PyJWT): access-токен с TTL 30 минут и refresh-токен с TTL 7 дней. Пароли хешируются алгоритмом **Argon2** — победителем Password Hashing Competition 2015, рекомендованным OWASP.

### Структура API

API включает более 25 эндпоинтов, сгруппированных по ресурсам:

| Группа | Эндпоинты | Назначение |
|--------|-----------|------------|
| `/api/v1/auth` | 4 | Регистрация, вход, обновление токена, выход |
| `/api/v1/sessions` | 5 | CRUD сессий, список, история сообщений |
| `/api/v1/chat` | 2 | HTTP-режим чата (fallback без WS) |
| `/api/v1/tasks` | 4 | Генерация и управление задачами |
| `/api/v1/analytics` | 3 | mastery-профиль, прогресс по навыкам |
| `/ws/chat/{session_id}` | WS | Потоковый диалог |

Схема базы данных включает четыре таблицы: `users` (учётные записи), `sessions` (учебные сессии с метаданными), `messages` (история диалога с ролями user/assistant/system) и `refresh_tokens` (хранение refresh-токенов с TTL и revocation-флагом).

## Уровень AI Core

### Компоненты

AI Core объединяет несколько независимо развёртываемых подсистем, взаимодействующих через чётко определённые интерфейсы:

**Мультиагентный конвейер** (раздел 2.3) — основа обработки каждого хода диалога. Оркестратор (`AgentOrchestrator`) координирует последовательный вызов агентов Profiler → MentalModel → Planner → Tutor → Verifier с поддержкой graceful degradation при отказе любого из агентов.

**Knowledge Tracing** (раздел 2.4) — подсистема отслеживания знаний на основе Dual-модели (BKT + DKT). Персистентность — SQLite через SQLAlchemy.

**Knowledge Forge** — граф навыков с 40+ компетенциями и PersonalizedNavigator для диагностики пробелов. Персистентность — JSON-файл (~100 КБ), human-readable и git-diffable.

**PathSlime** — биоинспирированный генератор альтернативных учебных траекторий (раздел 2.3).

**RAG-подсистема** (раздел 2.5) — ChromaDB + sentence-transformers для семантического поиска контекста.

**LLMClient** — унифицированный клиент Ollama API, поддерживающий режимы generate() (one-shot) и generate_stream() (потоковый). Модель: Qwen3.5-9B в формате GGUF Q4_K_M.

### Схема взаимодействия уровней

```
[Браузер]
    │ HTTP REST / WebSocket
    ▼
[FastAPI + Starlette]
    │ async call
    ▼
[AgentOrchestrator]
    ├── [Knowledge Tracing: BKT+DKT]
    ├── [Knowledge Forge + PathSlime]
    ├── [RAG: ChromaDB]
    └── [LLMClient → Ollama → Qwen3.5-9B GGUF]
    │ sync generator → asyncio.Queue
    ▼
[WebSocket → Браузер]
```

Мост между синхронным генератором токенов LLM и асинхронным WebSocket-обработчиком описан подробно в разделе 2.6.

## Обоснование выбора LLM inference

Для деплоя языковой модели выбран **Ollama** — локальный inference-сервер, обеспечивающий следующие преимущества:

1. *GGUF-квантизация* (Q4_K_M) снижает требования к памяти с ~18 ГБ (bf16) до ~5,5 ГБ, что позволяет запускать Qwen3.5-9B на потребительском оборудовании.
2. *OpenAI-совместимый API* позволяет переключиться на любую альтернативную модель без изменений кода агентов.
3. *Встроенная поддержка thinking-режима* для Qwen3.5 через специальный Modelfile с директивами `RENDERER qwen3.5` и `PARSER qwen3.5`.
4. *Параллельные запросы* (--parallel 3 в llama-server) обеспечивают одновременное обслуживание нескольких пользователей без деградации TTFT.

Альтернативы — vLLM и TGI — требуют CUDA-GPU и не поддерживают CPU-only режим, что нарушает требование НФ-5 (портируемость). На high-end GPU-оборудовании разрыв в скорости между Ollama и vLLM незначителен (~6%) на single-stream нагрузке [см. в разделе 3.4].
