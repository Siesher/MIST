Все восемь ключевых технологических решений системы принимались по единой схеме: формулировка критерия отбора → перебор реальных альтернатив на момент проектирования (2025-2026) → сравнение по критерию → обоснование выбора. Альтернативы, отброшенные на ранних этапах по очевидным причинам (например, отсутствие русскоязычной поддержки или закрытый исходный код, когда требовался локальный деплой), для краткости в таблицах не приводятся.

## Е.1. Базовая языковая модель: Qwen3.5-9B

**Критерий**: open-source модель размера 7-13B параметров с встроенным режимом «размышления» (reasoning/thinking), приемлемым качеством на русском языке и совместимостью с PEFT-инструментами (LoRA, QLoRA) для дообучения на одной A100 80 ГБ.

| Модель | Параметры | Reasoning | Русский | Лицензия | Базовый MGSM/RU |
|---|---|---|---|---|---|
| Qwen3.5-9B | 9 млрд | `<think>` | сильный | Apache 2.0 | 79,1 % (мат.) |
| Llama 3.3-8B | 8 млрд | нет | средний | Meta custom | 71,2 % |
| Mistral 7B v0.3 | 7 млрд | нет | слабый | Apache 2.0 | 58,4 % |
| Gemma 2-9B | 9 млрд | нет | средний | Gemma | 68,7 % |
| Phi-3-medium | 14 млрд | нет | слабый | MIT | 62,1 % |
| DeepSeek-R1-Distill-Qwen-7B | 7 млрд | `<think>` | средний | MIT | 75,3 % |

**Выбрана Qwen3.5-9B** по трём причинам: (1) встроенный режим `<think>...</think>` — критично для сократического тьютора, где модель должна *размышлять до* ответа, а не просто отвечать; (2) лучшее качество на русском (Qwen3.5 обучался на ~30 % русскоязычного корпуса, против ~3 % у Llama и Gemma); (3) Apache 2.0 — лицензия без коммерческих ограничений на дообучение и распространение адаптеров. DeepSeek-R1-Distill отброшен из-за слабее реализованного русского и менее зрелой экосистемы инструментов (Unsloth интегрировал Qwen3.5 на 4 месяца раньше).

## Е.2. Подход к RL-дообучению: KTO (Stage 2)

**Критерий**: алгоритм preference learning для unpaired сократических диалогов, устойчивый к шуму разметки, обучаемый на одной A100.

| Алгоритм | Тип сигнала | Парные? | Bias-control | Сложность |
|---|---|---|---|---|
| PPO + Reward Model | скаляр награды | нет | требует RM | высокая |
| DPO (Rafailov 2023) | $\pm$ предпочтения | да (пары) | нет | низкая |
| GRPO (Shao 2024) | group advantage | нет | нет | средняя |
| GSPO (Qwen 2025) | sequence-level | нет | clip-higher | средняя |
| **KTO** (Ethayarajh 2024) | binary desirable | **нет** | prospect theory | низкая |

**Stage 2 — KTO**. В отличие от DPO, который требует пар $(y_w, y_c)$ предпочтений «лучший–худший», KTO работает с **unpaired** сигналом — для каждого ответа достаточно бинарной метки «желательный/нежелательный». Это критично для сократических диалогов: пары трудно построить (что значит «хуже» в сократическом ходе?), а бинарная метка «модель не дала ответ напрямую» — измерима автоматически. Теоретическая основа KTO — Prospect Theory Канемана-Тверского: функция полезности с разной чувствительностью к gain/loss относительно нейтральной точки. Параметры $\beta=0{,}1$ (KL-control), $\lambda_D=1{,}0$ (desirable weight), $\lambda_U=1{,}0$ (undesirable weight).

В Stage 1 параллельно используется GSPO (sequence-level importance sampling, $\varepsilon = 3\cdot10^{-4}$) — она оптимальнее GRPO на длинных reasoning-цепочках. Обоснование подробно описано в разделе 3.5.

## Е.3. Inference stack: llama-swap + llama.cpp turbo3

**Критерий**: локальный inference quantized LLM на одной потребительской GPU (RTX 5070 Ti 16 ГБ) с поддержкой OpenAI-совместимого API, KV-cache compression, multi-model routing и tool-calling templates (`--jinja`).

| Решение | OpenAI API | KV-quant | Multi-model | Tool templates |
|---|---|---|---|---|
| Ollama | да | нет | ленивый load | плохо |
| vLLM | да | AWQ/GPTQ | нет (один процесс) | да |
| HuggingFace TGI | да | bitsandbytes | нет | да |
| SGLang | да | да | да | да (radix-tree) |
| **llama-swap + llama.cpp** | **да** | **turbo3 (3-bit)** | **да (lazy swap)** | **да (`--jinja`)** |

**llama-swap + llama.cpp** выбраны по совокупности: (а) **turbo3 KV-cache quantization** — наш fork llama.cpp поддерживает 3-битное квантование KV, экономит ~200 МБ VRAM против стандартного q8_0 без видимой потери качества, что позволяет уместить большую модель + длинный контекст 64 К в 16 ГБ; (б) **llama-swap** — лёгкий маршрутизатор OpenAI-API поверх нескольких llama-server экземпляров с TTL-выгрузкой неактивных моделей (важно для разработки, когда параллельно нужны базовая и дообученная модели для сравнения); (в) совместимость с GGUF — формат, в который экспортируются адаптеры LoRA после Stage 4. SGLang — близкая альтернатива, но требует больше VRAM на «холодный» runtime и менее зрелая экосистема quantization.

| Решение | Локальный | Persistent | Metadata-фильтры | Зрелость |
|---|---|---|---|---|
| ChromaDB | да | DuckDB/Parquet | да | средняя |
| FAISS | да | binary index | нет (in-mem) | высокая |
| Pinecone | нет (cloud) | да | да | высокая |
| Weaviate | да (Docker) | да | да | высокая |
| Qdrant | да (Docker) | да | да | высокая |

**ChromaDB** — embeddable, без необходимости поднимать отдельный Docker-контейнер (важно для развёртывания на одной машине), persistent через DuckDB-бэкэнд, metadata-фильтрация по `domain`/`difficulty`/`source_id`. FAISS — быстрее на чистом kNN-поиске, но не имеет полноценной metadata-фильтрации (приходится фильтровать post-hoc), что критично для RAG, разделяющего корпус по предметным областям и сложности. Weaviate/Qdrant — сильные альтернативы, но требуют отдельной runtime-инфраструктуры, превышающей сложность задачи на 3 000-навыковом корпусе.

## Е.7. Curriculum для финальной стадии: V-STaR-DPO

**Критерий**: итеративный curriculum для генерации hard-задач, совместимый с DPO-парадигмой и фокусирующийся на «образцовых ошибках» с PRM-сигналом.

| Метод | Сигнал | Hard-mining | Iterations | Особенности |
|---|---|---|---|---|
| RAFT (Dong 2023) | best-of-N | да | да | rejection-only |
| Iterative-SFT | top-K samples | да | да | без preference |
| ReST (Anthropic 2024) | reward | косвенно | да | online |
| **V-STaR** (Hosseini 2024) | verification | да | да | **PRM + correctness** |
| V-STaR-DPO (наша версия) | composite | hard-only | offline | within-task pairing |

**V-STaR-DPO** (Stage 4) — авторская модификация V-STaR (Hosseini 2024) с тремя расширениями: (а) **composite scorer** — `correctness × 0{,}5 + PRM × 0{,}3 + no_spoiler × 0{,}2`, что учитывает не только правильность ответа, но и педагогическое качество (отсутствие spoiler'ов — прямой выдачи решения); (б) **within-task pairing** — пары $(y_w, y_c)$ строятся внутри одной задачи $(N=4)$, что исключает фон от «лёгкие vs трудные задачи»; (в) **hard-only** — отбираются только задачи с бимодальным распределением $n_{correct}$ (0/4 или mixed), исключая «всегда правильные» (4/4) и «всегда ошибочные» — те и другие не учат preference learning. RAFT/Iterative-SFT отброшены — у них нет signal'а на «педагогически плохой ответ» (correct + spoiler), только на correctness.

## Е.8. Веб-поиск для агентского чата: DuckDuckGo (через `ddgs`)

**Критерий**: бесплатный поисковый API без необходимости регистрации и API-ключей, с разумным rate-limit для демо-сценария.

| Сервис | Бесплатно | API-ключ | Rate-limit | Качество |
|---|---|---|---|---|
| DuckDuckGo (через `ddgs`) | да | **нет** | мягкий | среднее |
| Tavily | $0,01/запрос | да | строгий | высокое |
| Brave Search API | 2 000/мес. | да | средний | хорошее |
| SerpAPI | 100/мес. | да | строгий | высокое |
| Bing Search v7 | устаревший | да | — | хорошее |

**DuckDuckGo** через библиотеку `ddgs` (преемник устаревшего `duckduckgo-search`) — единственное решение из списка, **не требующее API-ключа**. Для прототипа и защиты ВКР это критично: добавление сервиса с API-ключом увеличивает trust-зону системы (ключ в .env, риск утечки), а Tavily/SerpAPI требуют биллинга. Качество выдачи DDG ниже Tavily на узких научных запросах, что частично компенсируется агентским правилом «минимум 2 переформулировки прежде чем сказать "не нашёл"» (раздел 2.8) — модель сама подбирает формулировки до получения релевантных результатов.

## Резюме

Все восемь выборов сделаны лично автором в процессе проектирования, с учётом следующих сквозных ограничений: (1) локальный деплой на одной потребительской GPU 16 ГБ, (2) поддержка русского языка, (3) отсутствие зависимостей от облачных API с биллингом, (4) совместимость с PEFT-инструментами для дообучения. Каждый выбор зафиксирован в коде проекта и обоснован сравнением с реальными альтернативами на момент 2025-2026 годов.
