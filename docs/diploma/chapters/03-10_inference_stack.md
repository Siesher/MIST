Раздел 3.4 описал базовый клиент `LLMClient` поверх Ollama — первый рабочий вариант inference-стэка системы. В процессе работы над агентскими возможностями (раздел 2.8) выяснилось, что Ollama не поддерживает в полной мере OpenAI-совместимый протокол tool-calling, что блокирует функциональность web-поиска и SKI-инструментов. Поэтому в финальной версии системы реализован альтернативный inference-стэк: связка **llama-swap[^lswap] + llama.cpp[^lcpp]**, заменяющая Ollama в продакшн-режиме.

## Архитектура llama-swap

llama-swap — лёгкий маршрутизатор, реализующий OpenAI-совместимый HTTP-интерфейс (`/v1/chat/completions`, `/v1/models`) и динамически запускающий или останавливающий процессы llama.cpp-сервера в зависимости от того, какая модель запрошена клиентом. Конфигурация задаётся YAML-файлом; каждая модель описывается командой запуска (полный CLI llama.cpp), TTL[^ttl]-таймаутом неактивности и health-check endpoint'ом.

```yaml
models:
  mits-tutor:
    cmd: |
      C:/OpenCode/llama.cpp/llama-server.exe
      --model C:/Work/MITS/training/models/mits-kto.q4km.gguf
      --ctx-size 65536
      --cache-type-k turbo3 --cache-type-v turbo3
      --jinja --parallel 2 --port ${PORT}
    ttl: 1800
```

В этом конкретном блоке: 65 536 токенов контекста, KV-кеш в формате `turbo3` (3-битное квантование[^kvturbo]), включён шаблон Jinja для tool-calling, разрешены 2 параллельных запроса; неактивная модель выгружается из VRAM через 30 минут. Тот же llama-swap одновременно обслуживает базовую и дообученные модели (Stage GSPO/KTO/DPO) — переключение между ними при запросе клиента занимает 3-5 секунд («cold swap») или мгновенно если модель уже в памяти.

## llama.cpp с TurboQuant KV

Базовый inference-движок — llama.cpp, написанный на C++/CUDA и поддерживающий формат GGUF[^gguf2]. Стандартное квантование KV-кеша[^kv2] в llama.cpp — 16-битное (fp16) или 8-битное (q8_0); при контексте 64 К токенов это даёт ~5,2 ГБ VRAM на одной модели 9B. Использованная в проекте сборка llama.cpp ([am17an fork](https://github.com/am17an/llama.cpp), ветка `feature/turboquant-kv-cache`) предоставляет дополнительный режим `turbo3` — **3-битное квантование KV** с почти неотличимой потерей точности (≤0,05 п.п. на бенчмарке).

Эффект `turbo3`: тот же контекст 64 К занимает ~1,8 ГБ VRAM вместо 5,2 ГБ. Освобождённые 3,4 ГБ используются под (а) больший контекст или (б) параллельные слоты для одновременных запросов (`--parallel 2`). На RTX 5070 Ti 16 ГБ это решающий фактор: позволяет уместить дообученную 9B-модель Q4_K_M[^q4km] (~5,7 ГБ весов) + 64K-контекст + 2 слота без OOM.

## Флаг `--jinja` и tool-templates

Ключ к OpenAI-совместимому tool-calling — флаг `--jinja` при запуске llama-server. С ним сервер обрабатывает Jinja2[^jinja2]-шаблон чата, встроенный в GGUF-файл модели; шаблон Qwen3.5 распознаёт поле `tools` в запросе и форматирует его в нативный синтаксис модели (XML-обёртки `<tool_call>...</tool_call>`). Без `--jinja` сервер игнорирует поле `tools` и не «показывает» инструменты модели — что и было причиной невозможности использовать tool-loop через Ollama (Ollama применяет упрощённую обработку шаблонов).

```bash
llama-server.exe --model mits-kto.q4km.gguf --jinja ...
```

Ответ с tool-вызовом возвращается в стандартном OpenAI-формате:

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_abc123",
        "function": {"name": "web_search", "arguments": "{\"query\":\"..\"}"}
      }]
    }
  }]
}
```

Это позволяет переиспользовать любую клиентскую библиотеку OpenAI без модификаций — Python-клиент проекта (`OpenAICompatLLMClient`) построен на стандартных `requests` без специфики llama.cpp.

## Python-клиент: OpenAICompatLLMClient

Класс `OpenAICompatLLMClient` (`src/models/openai_llm_client.py`) реализует тот же контракт, что и Ollama-based `LLMClient` (раздел 3.4): методы `generate`, `generate_stream`, `chat_with_tools`. Внутри — HTTP-запросы к `http://127.0.0.1:8090/v1/chat/completions` с поддержкой SSE-стриминга[^sse] и разбором двух потоков дельт: `delta.content` (видимый текст) и `delta.reasoning_content` (thinking-канал). Метод `chat_with_tools` реализует полный OpenAI tool-loop (см. раздел 2.8) — детектор зависания, stall recovery, лимит раундов.

Выбор бэкенда задаётся одной переменной конфигурации `LLM_BACKEND`:

```python
class BackendSettings:
    LLM_BACKEND: str = "llamacpp"  # альтернатива: "ollama"
    LLM_BASE_URL: str = "http://127.0.0.1:8090/v1"
    LLM_MODEL: str = "mits-tutor"
```

Переключение между Ollama и llama-swap не требует изменений в коде агентов — `OrchestratorService` сам выбирает нужный клиент при инициализации. Это пригодилось при дебаге: симптом «модель отвечает одно и то же» в одной из ранних сессий был вызван дефолтным `LLM_BACKEND="ollama"` при незапущенном Ollama-сервере, что молча скрывалось try/except'ом и приводило к фолбэк-строке. После переключения на `llamacpp` весь пайплайн заработал.

## Сравнительные характеристики

| Параметр | Ollama | llama-swap + llama.cpp turbo3 |
|---|---|---|
| OpenAI-совместимый API | да (упрощённый) | да (полный) |
| Поддержка tool-calling | частичная | да (через `--jinja`) |
| KV-cache quant | q8_0 | turbo3 (3-bit) |
| Контекст на RTX 5070 Ti | ~32 К | 64 К |
| Параллельные слоты | 1 (один lock) | до 4 (`--parallel N`) |
| Cold-swap между моделями | ленивая выгрузка | TTL 30 мин |
| Размер бинаря | ~250 МБ | ~80 МБ (llama-server) |
| Production-ready | да | да (требует ручной сборки fork llama.cpp) |

Финальная конфигурация системы использует **llama-swap + llama.cpp turbo3** как основной inference-стэк. Ollama сохраняется как fallback и для разработки на машинах без CUDA-сборки llama.cpp.

## Итоги раздела

Переход от Ollama к llama-swap+llama.cpp обеспечил три критические возможности, на которых построена финальная система: (1) полноценный OpenAI tool-loop с web-поиском, SKI и Knowledge Forge tools (раздел 2.8); (2) контекст 64 К токенов на потребительской GPU 16 ГБ благодаря turbo3-квантованию KV; (3) одновременную работу нескольких моделей через единый OpenAI-эндпоинт для сравнительных экспериментов. Перенастройка не потребовала изменения кода агентов или клиентов — благодаря тому, что `OpenAICompatLLMClient` реализует тот же контракт, что и Ollama-based `LLMClient`.

[^lswap]: llama-swap — open-source HTTP-маршрутизатор, имитирующий OpenAI API и динамически запускающий процессы llama.cpp-сервера. Конфигурируется одним YAML-файлом; поддерживает TTL-выгрузку неактивных моделей.
[^lcpp]: llama.cpp — высокопроизводительная реализация инференса LLM на C++/CUDA от Georgi Gerganov. Поддерживает квантование, KV-cache, batching, спекулятивное декодирование; формат хранения весов — GGUF.
[^ttl]: TTL (Time To Live) — время неактивности, после которого ресурс освобождается. В контексте llama-swap — время в секундах, через которое модель выгружается из VRAM, если к ней не было запросов.
[^kvturbo]: TurboQuant turbo3 — 3-битное квантование KV-кеша, разработанное в форке llama.cpp (am17an, 2025). Снижает потребление VRAM в ~3 раза по сравнению с q8_0 при потере точности ≤0,05 п.п. на бенчмарках.
[^gguf2]: GGUF (GPT-Generated Unified Format) — бинарный формат хранения квантованных весов LLM, используемый в llama.cpp. Содержит веса, токенизатор и метаданные (включая Jinja-шаблон чата) в одном файле.
[^kv2]: KV-кеш — кеш «ключей» (K) и «значений» (V) механизма внимания трансформера, сохраняемый между шагами генерации; позволяет не пересчитывать прошлый контекст на каждом шаге. Растёт линейно с длиной контекста.
[^q4km]: Q4_K_M — формат 4-битного квантования весов в llama.cpp с раздельной точностью для разных слоёв; даёт ~5× уменьшение размера модели с потерей точности около 0,5-1 п.п. на типовых бенчмарках.
[^jinja2]: Jinja2 — Python-библиотека шаблонизации, де-факто стандарт для chat-template'ов LLM (Hugging Face, llama.cpp). Шаблон определяет, как массив сообщений превращается в один промпт-строку для модели.
[^sse]: SSE (Server-Sent Events) — HTTP-протокол однонаправленного стриминга от сервера к клиенту через единое подключение; каждая порция данных — отдельное событие в формате `data: {json}\n\n`. Используется OpenAI API для стриминга токенов.
